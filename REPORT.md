## Views, Worker & Concurrency (from `bookings/views.py`)
- An in-memory queuing + worker approach:
  - `process_queue` (queue.Queue) holds pending process dicts.
  - `processes` dict maps pid -> process state for status reporting.
  - `booking_worker()` runs in a daemon thread started at module import and uses `fcfs_scheduling()` (first-come-first-served).
  - `room_semaphores` keep a `threading.Semaphore` per room keyed by `room_id`, initialized from `room.available_slots`.
  - Uses `transaction.atomic()` and `select_for_update()` to decrement `available_slots` safely inside DB transaction.
  - Releases semaphores in `finally` block when acquired.

Behavioral endpoints (bookings app, mounted under `/api/`):

## Observations & Potential Issues
- Background thread started at import-time in `views.py`: this will spawn a worker thread on every process start and can be problematic across Django auto-reloads, multiple workers, or WSGI/ASGI processes. Consider using a dedicated task runner (Celery, Django-Q, or a management command / systemd service) instead.
- Global mutable state (`processes`, `process_queue`, `room_semaphores`, `pid_counter`) is in-memory and will not persist across process restarts or across multiple worker processes.
- `generate_pid()` increments a global counter; pids are ephemeral and not stored persistently.
- `requirements.txt` appears to be UTF-16 encoded — `pip` may fail to parse it unless re-saved as UTF-8. Re-save or run: `python -c "open('requirements.txt','rb').read().decode('utf-16')"` to inspect, or convert file encoding.
- `front.html` uses double slashes in API URLs (`//api/...`) — browsers tolerate this but it's cleaner to use single slash.
- `make_booking` accepts `room_id` and `user_name` but performs no input validation (e.g., missing fields, type checks).
- No authentication or permission checks — endpoints are open.
- Error handling is basic; some exceptions are swallowed and exposed as plain text statuses in `processes` entries.
- Running a long-lived worker thread inside Django view modules may prevent clean shutdown and complicate testing.

## Security & Hardening Recommendations
- Move background processing to a proper worker (Celery or Django management command + external process).
- Remove or reduce `CORS_ALLOW_ALL_ORIGINS` for production; tighten `ALLOWED_HOSTS` and CORS origins.
- Add input validation and use DRF `APIView` or `ViewSet` with serializers to validate incoming data.
- Add authentication (token/session) and permission classes for booking endpoints.
- Replace global in-memory state with a persistent queue (Redis, RabbitMQ) or DB-backed task table.
- Add logging and structured error responses.
